# Gap analysis

Vael benchmarked against Google Material Design 3, IBM Carbon, Microsoft Fluent 2, Atlassian, Shopify Polaris, and Salesforce Lightning — scoped to gaps relevant to data-dense internal operations software.

## Foundation token gaps

| Gap | Priority | Notes |
| --- | --- | --- |
| Border / stroke tokens (border-subtle, border-strong, border-interactive) | High | Used constantly in tables and form fields; currently derived ad hoc |
| Density tokens (compact / default / comfortable row heights) | High | Power users need compact density in data-dense views. Carbon has `$layout-density`. |
| Focus ring tokens (color, width, offset) | High | Keyboard nav for power users; currently implicit via MUI defaults only |
| Mono / code typography tokens | High | Server params, log output, config values all need formal mono tokens. Carbon has `$code-01`, `$code-02`. |
| Z-index / layer scale | Medium | Vael has elevation shadows but no z-index token layer |
| Reduced-motion token flag | Medium | WCAG requirement; prefers-reduced-motion not formally tokenized |
| Interactive state layer tokens (hover/pressed opacity ramp) | Medium | Vael uses MUI action tokens but lacks an explicit opacity ramp. Material 3 and Fluent 2 define this. |
| Semantic surface tokens (surface-container, surface-dim, on-surface-variant) | Medium | Reduces hardcoded paper/background overrides |
| Shape scale (shape-small, shape-medium, shape-large, shape-full) | Low | Single border-radius works but limits systematic corner treatment |

## Component gaps

Components present in benchmarked systems not currently covered by Vael (MUI + MUI X + AG Grid + React Flow). Several of the High/Medium items below have **shipped since this analysis** — marked ✅ — as part of rounding out the dashboard and form layers.

| Component | Priority | Who has it | Notes |
| --- | --- | --- | --- |
| Number input / spinner | High | Carbon, Fluent 2 | ✅ **Shipped** as `InputNumber` — stepper + min/max/step |
| Status indicator / traffic light | High | All 6 systems | Job states, server health, alarm states — dot + label + semantic color |
| Structured list / definition list | High | Carbon, Atlassian | Label-value pairs, read-only. Metadata panels, job summaries, project details. |
| Stat / KPI tile | High | Carbon, Atlassian, Polaris | ✅ **Shipped** as `StatCard` — metric + `TrendBadge` + inline sparkline |
| Tag (distinct from Chip) | High | Atlassian, Polaris, Carbon | Read-only, semantic color mapping. Chip implies interactivity; Tag is display-only. |
| Notification center | High | Carbon, Fluent 2 | Bell icon opening an event feed panel. Core software surface for alarm log and system events. |
| Inline edit | High | Carbon, Atlassian | Click-to-edit in place, no Dialog required. Project config parameter tweaking. |
| Date/time range picker (unified start+end) | High | Carbon, Fluent 2 | Job windows and metric query ranges need a unified range picker. MUI X has two separate pickers only. |
| Side panel / detail panel | High | Carbon, Fluent 2 | Persistent split-view aside, not a Drawer. Job detail alongside table is a pervasive UI pattern. |
| Code block / syntax highlight | Medium | Carbon, Atlassian | API keys, config snippets, log output |
| File uploader / dropzone | Medium | Carbon, Polaris, Atlassian | ✅ **Shipped** as `FileUpload` — drag-drop dropzone + file list |

## Documentation gaps

| Gap | Priority | Who has it | Notes |
| --- | --- | --- | --- |
| Data formatting guide (numbers, units, scientific notation, timestamps) | High | None — Vael opportunity | Critical for a data product. No benchmarked system covers numeric data formatting. Vael should define this. |
| Chart / data viz usage guidelines | High | Carbon | Highcharts tokens exist but no guidance on chart type selection, axis labels, color encoding, or chart accessibility |
| Per-component a11y spec (keyboard behavior, ARIA roles, screen reader notes) | High | Carbon, Fluent 2 | Vael has a QA checklist but no per-component a11y documentation |
| Component status / maturity labels in docs | High | Carbon, Atlassian, Polaris | Vael has ADRs and audit matrix but no visible per-component status label |
| Error message writing guide | Medium | Polaris, Carbon | Voice & tone exists but no error-specific guidance (system errors vs. user errors, recovery language) |
| Token usage guidelines (when to use which semantic token) | Medium | Material 3, Atlassian | Vael documents that tokens exist but not the rationale for choosing one over another |
| Motion principles (when to animate, what not to animate) | Medium | Material 3, Fluent 2, Atlassian | Partial motion tokens exist but no narrative principles or reduce-motion guidance |

## Real-time / streaming data display pattern

None of the six benchmarked systems have a formalized pattern for live-updating metric values, stale data indicators, or alarm escalation states. This is entirely domain-specific to monitoring and operations software — and the highest-leverage area for Vael to define something that no other design system has.

### What this pattern library could include

- **Live value component** — current reading + unit + freshness indicator
- **Stale data indicator** — value grayed out when the metric feed drops
- **Alarm state escalation** — info → warning → critical with visual + audio cues
- **Telemetry sparkline** — inline mini-chart for trend-at-a-glance
- **Metric card** — threshold vs. actual, deviation indicator
- **Event timeline** — system events overlaid on metric data

## Marketing & website surfaces

> **Scope note:** the benchmark above is scoped to internal operations software. This section
> extends that scope to the **marketing/website** surfaces Vael must cover so the **A Focused Design
> site** ([`afd-website`](https://github.com/catherinebhicks/afd-website), HubSpot build) can be
> assembled entirely from Vael rather than one-off CSS. Governing rule: every AFD design decision
> comes from Vael as-is, or is a gap listed here to complete **before** it's used on the site.
> Audited against Vael 2026-07-13.

| Surface | Priority | Status | Basis / what's needed |
| --- | --- | --- | --- |
| Case-study page layout | — | ✅ **Composable — no new component** | Assemble from `SlideSection` + `SectionHeading` + `PullQuote` + `StatCard` + `Card` + `BrowserFrame`. The repo's own `case-study/` proves the composition. |
| Marketing hero (headline + CTA + visual) | High | ⚠️ **Variant needed** | `SlideSection` + `SectionHeading` give a full-height section scaffold but render no CTA button or hero visual. Add a hero variant with a CTA slot + media slot. |
| Testimonial block (quote + attribution) | Medium | ⚠️ **Variant needed** | `PullQuote` is ~90% there (mono statement + accent rule + subtext). Add an attribution affordance (author · role · company · optional avatar). |
| Pricing table / offer cards | High | ❌ **Gap** | No pricing component anywhere; only raw `Card`. Needs a tiered pricing/offer card set with feature rows + CTA. |
| Client logo-strip / marquee | Medium | ❌ **Gap** | No multi-logo row exists (`BrandLogo` is a single product wordmark). Needs a responsive client-logo strip with alt-text-first markup (matters for AI-search proof-as-text). |
| Marketing footer | High | ❌ **Gap** | Every `footer` in the system is a table/chart-card footer. Needs a site footer: nav columns, legal, social, newsletter slot. |
| Blog / article layout | Medium | ❌ **Gap** | No long-form content template (system is scoped to data-dense UI). Needs an article/blog reading layout (prose measure, headings, figure, pull-quote, TOC optional). |
| `BrandLogo` component | Medium | ❌ **Gap (referenced, not built)** | Referenced in `AppBar` docs but absent from `src/components/`. Needs a real slot-based brand-logo component so any brand (incl. AFD's "@" mark + favicon, supplied by the AFD theme) can drop in. |

**Gates on the AFD side** (`afd-website` Epic H): hero + footer + logo-strip → **H15** (core pages); pricing/offer cards → **H16** (landing pages); blog/article → **H12** (blog); `BrandLogo` → **H3** (theme setup). Case-study layout is **not** a blocker (composable), so **H13/H14** can proceed on existing components.
