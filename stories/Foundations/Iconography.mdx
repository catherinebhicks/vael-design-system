## One library, consistent weights, precise sizing

FontAwesome is the single icon source. No other icon libraries are permitted — not Material Icons, not ad-hoc SVG sets, not emoji. Consistency across every screen depends on this rule.

### The rule

- Icons are rendered with the FontAwesome React component from `@fortawesome/react-fontawesome`.
- Two weights ship by default: **Regular** (`@fortawesome/free-regular-svg-icons`) and **Solid** (`@fortawesome/free-solid-svg-icons`).
- **Never** add `@mui/icons-material` imports — this is the one hard prohibition, upheld by convention in review (there is no lint rule wired up to catch it, so the discipline is on the author).
- Keep weight consistent within a view — don't mix Regular and Solid in the same toolbar.

**Light weight and the extended set.** A third weight (Light) and FontAwesome's full ~30,000-icon catalog are available if a project adds a FontAwesome **Pro** license and the corresponding `@fortawesome/pro-*-svg-icons` packages. The design language is the same; only the licensed set differs. Out of the box, Vael documents and ships the Free Regular + Solid weights.

### Why FontAwesome over Material Icons?

Material Icons ships in a fixed set of variants at a single optical size. FontAwesome gives a real weight hierarchy (Regular for the default UI, Solid for emphasis and active states) and a broader, more technical icon vocabulary — a better fit for data and admin tooling.

## Weight semantics

| Weight | Import | When to use |
| --- | --- | --- |
| Regular (default) | `free-regular-svg-icons` | The default for all inline UI — lists, navigation, inline actions, input adornments, icon buttons. Balanced stroke weight. |
| Solid | `free-solid-svg-icons` | Active or selected states (a filled star vs. an outlined one), error / warning states where urgency matters, and high-emphasis actions. Fills add visual weight. |

Solid is commonly paired with Regular to show state changes: a Regular star means "not favorited," a Solid star means "favorited." This convention should be preferred over color changes alone.

## Size tokens

| Token | Size | Usage |
| --- | --- | --- |
| small | 20px | Dense UI (table headers, compact list items), inline with 14px text |
| medium (default) | 24px | Buttons, nav items, list icons, most interactive contexts |
| large | 35px | Feature callouts, empty-state illustrations, major action cards |
| inherit | parent font-size | Inline within a paragraph or heading — scales with surrounding text |

Why 20 / 24 / 35? 24px pairs well with 16px body text. 20px matches the cap height of 14px `body2` text for dense inline contexts. 35px is the "display" size for empty states and feature callouts — larger than 24 but small enough not to read as an illustration. Arbitrary sizes (e.g. 28px, 40px) are discouraged — if you need something between tokens, use `inherit` and set the parent font-size.

## Color

Icons inherit `color` from their parent by default. Specific rules:

- Default icons → `text.secondary` (60%) — decorative or supporting.
- Interactive icons (buttons, nav) → `text.primary` (87%).
- Active / selected icons → `primary.main`.
- Error / warning icons → `error.main` / `warning.main`.
- Success icons → `success.main`.
- Disabled icons → `action.disabled`.

Never apply custom hex colors directly to an icon — route through semantic tokens so icons respect future theming (e.g. dark mode).

## Accessibility

- Decorative icons must have `aria-hidden="true"` so screen readers skip them.
- Interactive icon-only buttons must have an accessible label via `aria-label` or a visible tooltip.
- Icon + text pairs — make the icon `aria-hidden` and let the text be the accessible label.
- Never use an icon alone to convey meaning — pair with text, or a tooltip as a minimum.
- Hit targets for icon-only buttons must be at least 44×44px — wrap in an `IconButton` with adequate padding.

## Common pitfalls

- **Importing `@mui/icons-material`** — the one prohibited source. Use FontAwesome.
- **Mixing weights in a toolbar** — pick one weight per visual group. Toolbars, nav, and button rows should all use Regular unless an item expresses active state via Solid.
- **Icons as load-bearing labels** — an icon of a server doesn't reliably mean "job" or "project" to every user. Always include text.
- **Ad-hoc inline SVG** — if an icon you need isn't in the installed set, add the package (or a Pro license) rather than maintaining a parallel asset set — that's how icon systems fragment.
